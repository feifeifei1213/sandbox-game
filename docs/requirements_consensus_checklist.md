## 3. 已确认共识

### 3.1 项目定位与首版范围

- `已确认`
- 本项目首版以公司活动使用为目标，教育和演练意义更强。
- 首版目标是先做出“可调试初版系统”，优先保证规则正确、流程可走通。
- 首版只做：`Excel 已承载的规则 + 少量必要流程控制`。
- 当前桌游纸面流程暂不完整电子化，但系统设计应尽量不阻断后续电子化扩展。

### 3.2 角色与数据权限

- `已确认`
- 系统角色分为：
  - 玩家组账号
  - 管理员账号
- 总共有 `10` 个参赛组账号。
- 每组在系统中按 `1 个操作账号` 建模。
- 玩家之间数据隔离，不能查看彼此经营数据。
- 管理员可查看所有组数据。
- 汇总页仅管理员可见。
- 管理员允许通过普通通知向全体公开赛事事件信息，例如 `第一小组已破产`；这属于赛事信息公开，不等同于开放经营明细。

### 3.2.1 首版登录闭环

- `已确认`
- 系统提供统一登录页。
- 用户通过用户名和密码登录。
- 系统根据账号角色自动跳转，不要求用户手动选择角色。
- 玩家登录成功后默认进入 `0年经营`。
- 管理员登录成功后默认进入管理端首页；首版默认落在 `汇总页`。
- 系统提供退出登录动作，退出后回到统一登录页。
- 首版登录仅做最小认证闭环，不扩展复杂账号管理能力。

### 3.3 年份与年度定位

- `已确认`
- 存在 `初始基线`、`0年经营/财报`、`1年~最终年经营/财报`。
- `初始基线`：
  - 由管理员录入或确认
  - 提交后锁定，不可修改
- `0年`：
  - 是引导年 / 非排名年
  - 玩家可正常填写和提交
  - 参与到 `1年` 的数据传递
  - 不进入正式汇总和最终排名
- `1年 ~ 最终年`：
  - 为正式比赛年
  - 进入汇总
  - 参与最终胜负判定

### 3.4 年度推进与阶段推进

- `已确认`
- 季度推进由各组自行决定，通过阶段提交推进。
- 年度推进不由玩家决定，由管理员统一开放下一年。
- `0年` 与正式年份流程一致，主持人在线下讲解，不在系统内增加特殊“教学模式”。
- `0年` 不需要线上订单，是管理员带领玩家熟悉规则的年份。
- `1年` 起正式年份需要先完成年度订单流程，再进入经营页 Q1 正式提交。
- 年份标签页全部可见，未开放年份不可进入。

### 3.4.1 单组演练支持边界

- `已确认`
- 单组演练库 / 单组演练模式属于开发、测试、联调、验收支持能力，不改变正式比赛规则。
- 正式比赛中，管理员开放下一年仍要求“全部未破产组完成当前开放年份财报”。
- 推荐通过“正式比赛库 / 多组演练库 / 单组演练库”分离来支持不同用途。
- 单组演练环境推荐仅初始化 `1` 个管理员账号与 `1` 个玩家组账号，便于重复跑 `0年 -> 最终年` 主链。

### 3.4.2 赛前初始化小组数量

- `已确认`
- 需要支持赛前初始化可配置小组数量。
- 不需要支持比赛进行中动态增减小组数量。
- 初始化完成后，系统以后端已初始化的小组主数据作为唯一运行依据。
- 首版建议直接以后端 `sg_group` 实际记录数推断 `initialized` 与 `groupCount`。
- 管理员提交初始基线时，按当前已初始化的小组集合进行扇出应用。
- 汇总页、最终排名区、组数据页、通知与奖惩目标范围，均按实际初始化的小组数据动态适配。
- 若需变更小组数量，应重新初始化新的比赛环境或新的比赛库。

### 3.5 玩家端页面方向

- `已确认`
- 玩家端经营页采用高保真 Excel 风格整页布局。
- 玩家端新增独立 `年度订单` 页，不把订单选择流程塞进经营页主表。
- 玩家端财报页也采用高保真 Excel 风格整页布局。
- 首页默认进入 `0年经营`。
- 页面中所有阶段区域尽量完整展示，不拆成多个碎页面。
- 未开放阶段的区域保持可见，但输入格为锁定态，不可编辑。
- 右侧允许存在轻量工作栏，但主表必须是页面主体，不能破坏 Excel 感。
- 玩家端右侧工作栏顶部应放置通知区，优先展示管理员最新通知。

### 3.5.1 线上订单与市场竞标

- `已确认`
- 线上订单从 `1年` 开始，`0年` 不需要订单。
- 订单市场、订单类型、每年最大标段数和默认市场开启状态由当前订单模板定义；全部模板取消每标段固定订单卡数量上限，数量仍必须为非负整数。
- 当前贵宾订单模板 `VIP_ORDER_TEMPLATE_V1`：市场为本地市场、区域市场、全国市场、全球市场；订单类型为代办过检、两舱贵宾、商务贵宾、会员定制；每年最多 `16` 个标段；本地市场默认开启，区域市场、全国市场、全球市场默认关闭。
- 当前机场订单模板 `AIRPORT_ORDER_TEMPLATE_V1`：市场为国内市场、国际市场；订单类型为窄体、宽体；每年最多 `4` 个标段；国内市场默认开启，国际市场默认关闭。
- 管理员按当前订单模板在当年订单流程中手动开启或关闭市场。
- 未开启市场不生成订单池、不进入标段释放顺序、不进入抢单流程。
- 每个 `市场 + 订单类型` 组合视为一个独立标段。
- 管理员需要配置标段释放顺序，系统按释放顺序逐个开标。
- 管理员开标前配置全年全部标段释放顺序；释放第一个标段后不允许调整。
- 玩家在正式年份开标前一次性提交本年当前订单模板下全部 `市场 + 订单类型` 投入值；贵宾模板为 `16` 项，机场模板为 `4` 项；已开启市场均必填，允许填 `0`，空值不允许提交。
- 未开启市场对应的全部投入由系统自动按 `0` 提交，玩家端输入禁用；绕过前端提交非 `0` 时服务端禁止提交。
- 管理员可按 `年份 + 市场` 配置单市场投入上限；空值表示无上限，非空时必须为非负整数，单位为 `M`。
- 已有任意小组提交本年市场投入后，管理员不能再修改本年市场开启状态和单市场投入上限。
- 开标前置条件为：所有未破产小组已提交当年市场投入、当年订单池已确认、当年标段释放顺序已配置。
- 当前标段结束后，由管理员按预设顺序手动释放下一标段，不能跳序，系统不自动释放下一标段。
- 未开启市场显示为“市场未开启”，订单数量为 `0` 的已开启标段显示为“未配置订单”，两者均不进入开标；只有订单数量大于 `0` 但因全员无投入等流程原因未进入选单时，才显示为“已跳过”。
- 任何小组在某标段投入为 `0` 时均无该标段选单资格，市场龙头也不例外；龙头只影响顺序，不增加资格或数量。
- 贵宾服务版和生产制造版采用固定 `3 / 6 / 9` 多轮门槛：投入 `1~2 / 3~5 / 6~8 / >=9` 分别最多参加 `1 / 2 / 3 / 4` 轮；机场版暂时保持单轮。
- 每个标段只生成一次基础顺序，后续轮次只按资格过滤，不重新排序或随机；每个小组每轮最多选择 `1` 个订单。
- 释放标段后自动开始第一轮；后续有效轮次由管理员点击“开启下一轮”，空轮自动跳过，当前标段全部有效轮次完成前不能释放下一标段。
- 任意轮次订单池提前选空时立即结束整个标段；全部有效轮次结束后剩余订单标记为 `UNSELECTED_EXPIRED`，只保留审计记录。
- 订单被选后锁定，后续小组不可再选。
- 只有当前轮到的小组可以选单；没轮到的小组只能查看。
- 当前轮到的小组可放弃本轮，确认后不可反悔，但后续有资格轮次仍可参加；玩家放弃需要确认但不填原因。管理员可代为跳过当前轮长时间未操作的小组，必须填写原因，但不能代选订单。
- 玩家选单后不能撤销；首版也不做管理员撤销。
- 玩家不显示其他组已选订单明细，已被选择的订单在玩家端显示为灰色不可选。
- 管理员端可纵向查看当前标段全部轮次的完整顺序和各组状态；玩家端只查看本组状态和当前轮次，不展示其他小组未来轮次顺序或排序依据。
- 订单状态同步采用 `3` 秒自动轮询，不做 WebSocket；玩家端轮询必须静默刷新，不触发整页加载态，不导致页面跳回顶部。

### 3.5.2 选单顺序与市场龙头

- `已确认`
- `1年` 按当前标段投入从高到低确定选单顺序。
- 当前标段投入相同时，通过随机方式确定先后，并记录随机结果。
- `2年` 起，同一市场下各标段先由上一年该市场市场龙头优先选择，再由其他参与小组按当前标段投入排序。
- 市场龙头只在对应市场生效，不跨市场。
- 市场龙头只在未破产小组中生效；若上一年市场龙头已破产，本年按没有有效市场龙头处理。
- 市场龙头当年当前标段投入为 `0` 时无资格；投入金额仍按实际 `0` 计入经营页。
- 若上一年该市场没有任何已选订单，则本年不产生市场龙头，直接按市场投入排序。
- 市场龙头按“上一年该市场全部订单类型已选订单金额合计最高的小组”确定。
- 每个市场每年只产生 `1` 个市场龙头；若上一年该市场已选订单金额并列最高，则随机确定市场龙头，并记录随机结果。
- 非龙头小组当前标段投入相同时，按上一年度该市场订单总额从高到低排序；仍相同则随机，并记录随机结果。
- 龙头按上一年该市场全部订单类型、全部轮次的已选订单金额合计确定，不要求订单交付；每年重新判定。
- 龙头和基础顺序在生成选单顺序时统一计算并固化为订单定序依据，不新增可恢复的订单快照。

### 3.5.3 订单交付与经营页联动

- `已确认`
- 正式年份本年订单竞标流程未结束时，不允许进入或提交经营页 `Q1`。
- 当前订单模板下全部市场投入合计进入经营页年初区 `市场投入`，并只读展示。
- 全部标段已选订单金额合计进入经营页 `订单总额`。
- 直接成本不由订单推算 Excel 决定，仍由玩家在经营页填写。
- 账期字段首版只展示，不参与经营页应收账款自动计算。
- 玩家在年度订单页或本组订单展示区对已选订单执行交付操作，交付时绑定当前经营季度。
- 订单不允许分季度拆分交付。
- 一个季度可交付多个完整订单。
- 订单交付不再校验玩家手工销售收入是否等于订单金额；交付成功后，系统按该季度当前有效已交付订单金额合计自动生成经营页销售收入。
- 正式年份经营页销售收入为系统只读联动项；直接成本仍由玩家手工填写。
- 订单页继续展示本组全部已选订单：待交付可操作，已交付灰色只读，旧交付因退回重提或恢复快照失效时恢复为待交付并保留历史提示。
- 年末仍未交付的订单标记为 `UNFINISHED`，但暂不阻断财报提交。
- 未交付处罚规则暂未确定；首版只记录状态并预留后续处罚规则接入口。

### 3.5.4 第 9 步订单数量留痕

- `已确认`
- 生产制造版记录基础产品、标准产品、精密产品、智能产品四类新供应链订单数量；贵宾服务版记录代办过检服务、两舱贵宾服务、商务贵宾服务、会员定制服务四类新服务订单数量。
- 按 `小组 + 年份 + 季度 + 类型` 独立保存，每一年的记录不向下一年复制或结转。
- 每格单位为“个”，只允许非负整数；当前季度四项均必填，没有订单时显式填写 `0`。
- 该数据只是玩家线下放置空桶订单的手工留痕凭证，不影响任何经营、财报、汇总、排名和正式订单模块公式。
- 现有阶段级退回重提与单组快照恢复必须支持修改该记录；目标季度及后续季度随经营页重新开放，旧提交、安全快照和补提版本继续保留。
- 不新增字段级直接修改或字段级回退入口。

### 3.6 经营页提交流程

- `已确认`
- 不做单独“年初提交”。
- `Q1 提交` 时一并提交 `年初区 + Q1 区`。
- `Q2/Q3/Q4` 各自单独提交。
- `年末区` 单独提交。
- 本年经营全部完成后，才开放本年财报页。

### 3.7 提交校验规则

- `已确认`
- 阶段提交时，仅校验当前阶段范围内的手工必填项。
- 已提交且已锁定的历史阶段，不重复进行必填完整性校验。
- 具体为：
  - `Q1 提交`：校验 `年初 + Q1`
  - `Q2 提交`：只校验 `Q2`
  - `Q3 提交`：只校验 `Q3`
  - `Q4 提交`：只校验 `Q4`
  - `年末提交`：只校验 `年末区手工项`
- 所有填写项默认空值，`0` 必须由用户显式填写。
- 首版不做重型“校验列表面板”，只做：
  - 顶部错误提示
  - 未填项高亮

### 3.8 现金核对与阶段提醒

- `已确认`
- 经营页主表保留“核对季末现金”展示行。
- 系统展示各季度对应的季末现金计算值，供玩家线下自检。
- 系统不采集现场现金，也不因现金差异阻断提交。
- 每个季度提交后，系统提醒玩家关注贷款更新。
- 该提醒仅为提醒，不做强制拦截。
- 管理员可向全体或单组发送普通通知，允许自由文本。
- 普通通知可用于流程提醒、赛事播报与现场主持说明。
- 奖励 / 罚款不再由玩家手动填写，改为管理员按 `组 + 年 + 季` 下发。
- 经营页中的 `额外支出 / 罚款`、`额外收入 / 奖励` 保留 Excel 位置，但改为玩家只读、系统自动带入。
- `折现费用` 继续由玩家填写。

### 3.9 财报页规则

- `已确认`
- 财报页只有在本年经营结束后才开放。
- 财报页中自动带出 Excel 可计算结果。
- 首版财报页以当前 Excel 中绿色单元格定义手工输入边界。
- 当前已确认的财报手工项包括：
  - 在制品
  - 成品
  - 材料
  - 所得税税率
- 所得税税率使用下拉框，选项限制为：
  - `0.25`
  - `0.15`
  - `0`
- 财报提交后，本年度完成。
- 财报提交时必须校验：
  - `总资产 = 总负债 + 总权益`
- 总监得分公式调整已确认，生产制造版与贵宾服务版统一执行：
  - 最佳销售总监得分从 `0年` 起按“截至当年订单总额累计值整体除以 `10`”计算，即 `S_y = (O_0 + ... + O_y) / 10`。
  - 跨年实现采用 `S_y = S_(y-1) + O_y / 10`，不得采用 `(S_(y-1) + O_y) / 10`，避免历史得分被重复除以 `10`。
  - 最佳 CEO 得分在五项总监最终得分合计基础上增加“当前年份所有者权益 / 2”；所有者权益取当年财报 `K19 / reportTotalEquity`。
  - 当年所有者权益为负时允许降低 CEO 得分；销售总监与 CEO 结果不额外取整，允许小数。
  - 最佳 CFO 中已有的权益影响继续保留，CEO 新增的“当前所有者权益 / 2”不与 CFO 项抵消。
  - 新公式从 `0年` 起追溯用于历史查询与后续年份承接；旧提交、旧快照不物理改写，回退重提按当前公式重新计算。
  - 后端是正式计算口径；前端实时预览直接复用后端已缩放的销售总监得分，只在受财报手工项影响的 CEO 预览中同步增加“预览所有者权益 / 2”，不得对销售总监得分二次除以 `10`。

- 不重开已结束轮次，不重新计算轮次资格；订单定序依据不是第二套可恢复快照。
- `退回重提` 和 `恢复快照` 都是恢复为待重提 / 失效草稿，不让旧数据直接重新生效；区别仅在草稿来源，退回重提基于当前库数据，恢复快照基于历史快照载荷。
- 目标阶段及后续阶段的旧订单交付记录保留为历史留痕 / 草稿参考，但不作为当前有效交付；对应订单恢复为待交付 / 可重新交付，玩家重新推进到对应阶段后可重新交付原订单，也可改交其他已选订单。
- 经营页销售收入只按重新确认后的当前有效交付记录生成；旧草稿或快照中的销售收入不直接进入新正式提交。
- 未来年份已选订单保持归属；等该组重新推进到对应年份时继续作为该组订单来源。
- 若该组尚未参与某个已生成顺序的标段，系统只提示风险，现场节奏由管理员控制。

### 4.2B 单组快照回退后的汇总、奖惩与年度控制

- `已确认`
- 普通通知不回退。
- 普通退回重提时全部有效奖惩继续保留；恢复快照时奖惩有效状态按目标快照时点恢复，原记录不物理删除。
- 单条奖惩纠错使用管理员端“作废奖惩”，不得依赖普通退回隐式失效。
- 目标节点之后的汇总结果失效，汇总页显示 `待重提`，不计入排名。
- 已破产小组不得通过退回重提或恢复快照恢复为 `NORMAL`。
- 只要存在未破产小组处于回退补提 / 待重提状态，管理员不能开放下一年。

### 4.2C 赛前配置与业务显示字典

- `已确认`
- 管理员端统一设置 `赛前配置` 页面，集中承载小组数量、最终年份、沙盘版本包、业务显示字典、初始基线入口和确认初始化。
- 赛前配置采用向导式流程：`比赛基础信息 -> 选择版本包 -> 选择/编辑字典方案 -> 初始基线入口 -> 确认初始化`。
- 初始化前初始基线应完成，但系统不强制拦截；确认初始化时只提示管理员核对。
- 版本包负责字段结构、公式版本、流程规则和默认字典；管理员只能赛前选择，初始化后不能切换。
- 业务显示字典只改显示名，不改变稳定字段编码、字段含义、公式、数据或流程。
- 可改显示名包括经营页字段、财报页字段、初始基线字段、市场、订单类型、订单页字段和市场预测图表中的市场/订单类型。
- 不通过字典修改 Q1/Q2/Q3/Q4、年末、财报、按钮、菜单、错误提示、系统状态和普通通知自由文本。
- 市场和订单类型数量由当前订单模板定义；字典只能修改当前模板内已有市场和订单类型的显示名，不能新增或删除。
- 经营页和财报页字段结构固定，只能改名，不能新增字段、隐藏字段或调整位置。
- 字典方案必须绑定版本包；可新建、编辑、删除。
- 比赛初始化时生成当前比赛字典快照；编辑或删除字典方案默认不影响当前比赛。
- 初始化后可解锁修改当前比赛显示名称，也可把同版本包字典方案整体应用到当前比赛；应用前需二次确认，展示变更数量和详情。
- 初始化后可恢复当前版本包默认名称，也可将当前比赛显示名称另存为字典方案。
- 字段名称配置表默认不显示稳定字段编码，只展示分类、所属页面/区块、当前名称和修改后名称。
- 字典显示名不允许为空，同一类业务名称原则上不重复；长度业务上不限制，但页面需处理长文本。
- 字典修改后玩家端和管理员端静默同步，不弹窗、不清空草稿、不重置输入、不滚动到顶部。
- 字典修改需记录日志，用于管理员解释现场名称变化和追溯。

### 4.3 汇总页是否直接显示排名序号

- `已确认`
- 首版不展示过程中的实时排名。
- 在最终年份完成后，管理员汇总页可展示最终排名。
- 排名依据为最终年份 `所有者权益` 由高到低。

### 4.4 已破产状态的展示方式

- `已确认`
- 汇总页增加单独 `经营状态` 列。
- 已破产组以红色 `已破产` 标签展示。
- 首版不采用整行染色作为唯一表达方式。

### 4.5 通知与奖惩改造

- `已确认`
- 玩家端右侧工作栏顶部新增通知区，优先展示管理员最新通知。
- 普通通知由管理员发送，可发全体或单组，可为自由文本。
- 管理员允许向全体广播赛事事件信息，例如 `第一小组已破产`。
- 奖励 / 罚款不再由玩家手动填写，改为管理员按目标小组当前操作年份结构化下发；年份和归属阶段均由系统根据该组当前状态自动判断，管理员不手工选择历史年份或季度。
- Q1、Q2、Q3、Q4、年末经营中均允许下发；财报填写或草稿阶段允许下发并统一归属 `YEAR_END`；财报正式提交或年份完成后必须先退回，小组破产后永久禁止。
- 经营页中 `额外支出 / 罚款`、`额外收入 / 奖励` 保留 Excel 位置，但改为玩家只读、系统自动带入。
- 奖罚两行增加独立“年末”列；`折现费用` 继续由玩家填写且不增加年末字段，年末位置仅显示 `--`。
- 奖罚沿用税前收入 / 支出口径，变化后重新计算经营结果、财报预览、所得税、现金和所有者权益。
- 下发和作废前均显示影响预览；奖罚记录不可编辑或物理删除，只能在小组未破产时由管理员作废并保留完整审计信息。
- 玩家端每 `3` 秒静默检查奖罚版本，只局部合并奖罚和派生计算结果，不覆盖未保存输入，不改变焦点、光标和滚动位置，不触发整页刷新。
- 奖罚导致现金小于 `0` 时立即生成破产快照并判定破产；快照不视为正式财报提交、不进入正常汇总和排名。
- 破产判定不可撤销，不新增解除破产功能；破产后奖罚操作冻结。
### 4.6 自动保存失败时的交互

- `已确认`
- 首版自动保存采用轻量方案：每 `5` 分钟自动保存一次草稿。
- 季度提交 / 年末提交 / 财报提交仍是唯一正式提交动作。
- 首版不做复杂的自动保存失败交互设计：
  - 不做持续红色失败状态条
  - 不做离开页面的未保存提醒
- 这意味着首版更偏“草稿兜底”，而不是“强可靠协同编辑”。

### 4.7 经营页与财报页右侧工作栏是否区分内容

- `已确认`
- 两类页面的右侧工作栏采用 `同布局、分内容` 方案。
- 经营页工作栏偏向：
  - 阶段状态
  - 季末现金展示说明
  - 贷款提醒
- 财报页工作栏偏向：
  - 平衡校验
  - 税率说明
  - 财报提交

### 4.8 正式技术方案与数据存储粒度

- `已确认`
- 首版采用 `轻中型 Web 方案`。
- 数据存储以 `业务字段` 为主，不按 Excel 每个单元格直接建库存储。
- 前端通过字段到页面位置的映射来还原 Excel 风格。

### 4.9 Excel 公式的正式实现策略

- `已确认`
- 当前以确认版 Excel 作为 `规则基线`。
- 系统不直接把 Excel 当运行引擎，而是按 `业务字段 + 计算规则` 实现。
- 每个关键计算字段都应保留对应的 Excel 来源说明，保证可追溯。
- 若后续只是少量公式调整，应尽量通过集中修改规则映射或计算逻辑完成。
- 若变更已经影响到：
  - 字段结构
  - 流程状态
  - 汇总口径
  - 跨表联动语义
  则应按 `需求变更` 重新确认，不能视作普通公式微调。

### 4.10 财报页是否需要更贴近 Excel 的原始布局

- `已确认`
- 财报页要求高保真贴近 Excel。
- 但首版不要求像素级 `1:1` 复刻。
- 验收重点是：
  - 主表结构接近
  - 色块和手工格位置接近
  - 自动计算区与说明区关系清晰

### 4.11 异常解锁后财报与汇总的失效规则

- `已确认`
- 若某组某年已完成财报提交，之后又被管理员执行异常解锁，则：
  - 该年财报结果自动失效
  - 该年汇总数据临时撤回
  - 若为经营页异常解锁，玩家需重新完成该年的后续经营提交，再重新提交财报
  - 若为财报页异常解锁，玩家只需重新提交财报
  - 财报重提成功后，该年数据再重新计入汇总

### 4.12 异常解锁目标粒度补充

- `已确认`
- 当前“按年份通用解锁”的口径不足以满足管理员现场纠错。
- 正式需求新增：异常解锁需支持目标类型 `OPERATING` / `REPORT`。
- 若管理员选择 `OPERATING`，系统必须继续要求选择回退阶段：`Q1 / Q2 / Q3 / Q4 / YEAR_END`。
- 若管理员选择 `OPERATING`，系统不得仅因为财报页仍可编辑就拒绝解锁经营页。
- `OPERATING` 解锁后，目标阶段之前的结果保持有效，目标阶段重新开放，后续经营阶段与财报结果失效。
- `REPORT` 解锁后，只回收财报结果，不额外放开经营页已锁定区。
- “整年直接回到 Q1_OPEN” 与“定向异常解锁”不是同一能力，暂不并入本轮，后续单独讨论。

### 4.13 失效草稿规则

- `已确认`
- 经营页回退到 `Q2` 时：
  - `Q1` 保持有效且只读
  - `Q2` 重新开放可编辑
  - `Q3 / Q4 / 年末 / 财报` 不清空原值，但全部转为 `失效草稿`
- `失效草稿` 不计入：
  - 当前有效经营结果
  - 当前有效财报结果
  - 管理员汇总
  - 下一年的正式结转
- 玩家重新提交到对应阶段后，该阶段结果才重新恢复有效。

## 6. 当前建议结论

基于目前共识，当前项目的首版产品判断可以先写成：

- 页面层：`高保真 Excel 风格`
- 规则层：`以 Excel 为主依据，但按业务规则实现`
- 流程层：`中等复杂度状态流转`
- 存储层：`业务字段存储 + 页面映射`
- 首版范围：`经营页 + 财报页 + 管理员汇总/控制 + 少量异常解锁`

也就是说：

- 这不是“纯展示型原型”
- 也不是“重平台型系统”
- 当前更接近 `轻中型方案`
