# 沙盘经营系统后端开发指南（正式版）

> 更新日期：2026-03-25  
> 适用方式：基于《正式需求文档（首版）》《技术选型细化文档（Go 方向） v0.1》《接口设计文档（正式版）》《数据库设计文档（正式版）》《Go 项目结构与首版开发拆分文档（正式版）》，定义首版 Go 后端的实现边界、目录分层、编码约定与交付要求。  
> 文档定位：本文件回答“后端代码应该怎么实现”，不替代接口文档、数据库文档和 SQL 脚本。

## 1. 适用范围

本指南适用于沙盘经营系统首版后端实现，包括：

- 玩家端经营页接口
- 玩家端财报页接口
- 管理员汇总与控制接口
- 状态机与规则计算层
- 数据访问、迁移、日志与测试

本文件不覆盖：

- 公司统一登录平台的内部实现
- 运维部署平台细节
- 前端页面实现规范

---

## 2. 技术与实现基线

### 2.1 当前推荐基线

首版后端推荐采用：

- Go：`1.22+`
- Web 框架：`Gin`
- 参数校验：`go-playground/validator`
- 配置管理：`Viper`
- 日志：`Zap`
- 数据库：`MySQL 8.x`
- 数据访问：首版推荐 `GORM`；若团队已有成熟 `sqlx/sqlc` 基座，可在不改变分层职责前提下替换
- 迁移工具：`golang-migrate`
- OpenAPI：`swaggo`
- 测试：`testing + testify + httptest`

### 2.2 选型边界

- 首版采用 `Go 单体应用`，不引入微服务拆分。
- 首版不引入工作流引擎。
- 首版不以 Excel 文件作为运行时计算引擎。
- 首版不按单元格坐标驱动业务模型。

### 2.3 与现有文档的承接关系

后端实现必须同时遵守以下文档：

- `docs/requirements_spec.md`
- `docs/minimal_state_machine.md`
- `docs/api_design.md`
- `docs/database_design.md`
- `docs/calculation_rule_spec.md`
- `docs/excel_field_mapping.md`
- `docs/go_project_structure.md`

若实现与上述文档冲突，以正式需求、接口、数据库、规则文档为准，不得擅自通过代码“改规则”。

## 3. 项目目录与分层建议

推荐目录如下：

```text
sandbox-game/
  cmd/server/
  configs/
  migrations/
  internal/
    app/
    config/
    http/
      handler/
      middleware/
      dto/
    service/
    repository/
    model/
    rules/
    state/
    assembler/
    enum/
  pkg/
  tests/
    http/
```

### 3.1 各层职责

| 目录 | 职责 |
|---|---|
| `cmd/server` | 启动入口、依赖装配、配置加载 |
| `internal/http/handler` | 路由层，仅做参数接收、权限前置、结果封装 |
| `internal/http/middleware` | 认证、日志、请求追踪、统一错误处理 |
| `internal/http/dto` | 请求与响应结构定义 |
| `internal/service` | 业务入口、事务、流程编排 |
| `internal/repository` | 数据读写，不承载业务决策 |
| `internal/model` | 领域模型与持久化结构 |
| `internal/rules` | 经营、财报、汇总计算规则 |
| `internal/state` | 年份状态、阶段状态、财报状态推进 |
| `internal/assembler` | 视图拼装与查询返回对象转换 |
| `internal/enum` | 状态枚举、常量、错误码定义 |
| `migrations` | 建表与升级脚本 |
| `tests/http` | `.http` 调试与回归用例 |

### 3.2 禁止事项

- 不在 `handler` 中写复杂业务规则。
- 不在 `repository` 中做状态推进决策。
- 不把经营阶段必填校验、财报平衡校验散落在多个层重复实现。
- 不把规则常量硬编码到前端再由后端“默认接受”。

## 4. 编码约定

### 4.1 Handler 层

- 路由风格统一遵循 `docs/api_design.md`。
- Handler 只负责：
  - 参数绑定
  - 参数基础校验
  - 调用 Service
  - 统一返回 `CommonResult` 风格结构
- 失败场景必须返回 `4xx/5xx`，禁止失败返回 `200`。
- 需要记录操作人的业务动作，统一从认证上下文读取，不由前端传入操作人名称。

### 4.2 Service 层

- 业务入口统一在 Service。
- 涉及写操作的主链路必须明确事务边界。
- 提交类接口必须按以下顺序处理：
  - 加载当前状态
  - 校验权限
  - 校验状态是否允许操作
  - 执行业务规则校验
  - 落正式提交或管理动作
  - 推进状态
  - 写日志或快照
- `提交经营阶段`、`提交财报`、`开放下一年`、`异常解锁` 都属于高风险写操作，必须单独保留方法，不与草稿保存复用同一入口。

### 4.3 Repository 层

- Repository 负责数据库查询与持久化。
- Repository 不得决定：
  - 是否允许提交
  - 是否允许解锁
  - 是否破产
  - 是否计入汇总
- 一组一年的当前有效状态查询应提供专门方法，避免业务层自行拼多表 SQL。

### 4.4 Rules 层

- 规则层必须独立于 Handler、Repository。
- 规则层至少拆成：
  - `operating_rules`
  - `report_rules`
  - `summary_rules`
  - `carry_forward_rules`
- 所有核心公式以 `docs/calculation_rule_spec.md` 为准。
- 规则层输出应尽量返回结构化结果，而不是零散 map。

### 4.5 State 层

- 状态推进必须统一进入 `state` 模块。
- 状态推进规则以 `docs/minimal_state_machine.md` 为准。
- `异常解锁` 是管理员动作，不应伪装成普通阶段状态。
- `BANKRUPT` 是叠加态，不替代年份主状态字段，但会影响后续所有写操作的可执行性。

### 4.6 注释规范（执行清单）

- 新增或修改 `public` 级别方法，必须补方法注释。
- 涉及状态推进、跨年传递、汇总撤回、破产判定的分支，必须补行内注释说明业务口径。
- 迁移脚本必须加中文注释说明“为什么要改”。
- 禁止空洞注释，例如“处理数据”“业务逻辑”。

注释样例：

- `// 业务约束：Q2 提交只校验 Q2 区，不重复校验已锁定的 Q1 区`
- `// 异常解锁后若财报已提交，需要先撤回汇总快照，再允许重提财报`
- `-- 作用：增加 sg_group_year_state(group_id, year_no) 唯一约束，保证一组一年只有一条主状态`

### 4.7 命名规范（执行清单）

- 包名、目录名：小写英文，避免拼音缩写。
- 结构体：`PascalCase`，职责后缀明确。
- 方法名：`camelCase`，动词开头。
- 布尔变量：使用 `is/has/can/should` 前缀。
- 常量：`UPPER_SNAKE_CASE`。
- 数据库字段：`snake_case`。
- 禁止使用 `tmp`、`obj`、`info1` 这类无语义命名。

## 5. 错误语义与异常处理

### 5.1 统一错误语义

后端错误语义必须遵守 `docs/api_design.md`：

- `400`：参数错误
- `401`：未登录
- `403`：无权限
- `404`：资源不存在
- `409`：状态冲突或重复动作
- `422`：业务规则不满足
- `500`：系统异常

### 5.2 本项目典型场景映射

| 场景 | HTTP 状态 |
|---|---|
| 年份不存在 | `404` |
| 当前年份未开放 | `422` |
| 当前阶段已提交，重复提交 | `409` |
| 当前阶段手工项不完整 | `422` |
| 财报平衡校验失败 | `422` |
| 破产组继续提交 | `422` |
| 下一年已开放，禁止解锁本年 | `422` |
| 无权限查看其他组数据 | `403` |

### 5.3 统一错误处理要求

- 业务错误必须返回可读的业务文案，不返回 SQL、堆栈等底层细节。
- 统一错误处理中间件要记录：
  - 请求路径
  - 请求方法
  - 操作人
  - 关键业务主键
  - 错误状态码
- 前端业务分支不得依赖错误文案，必须依赖状态码与结构化字段。

## 6. 数据迁移、初始化与配置

### 6.1 迁移规则

- 所有结构变更必须通过 `migrations/` 落脚本。
- 脚本命名遵循 `sandbox-game-upgrade-*.sql`。
- 脚本要尽量幂等。
- 结构变更后必须同步更新：
  - `docs/database_design.md`
  - `docs/implementation_plan.md`
  - 相关 Repository/Model

### 6.2 初始化数据

首版应至少提供以下初始化能力：

- 管理员账号
- 赛前可配置数量的组账号
- 赛前可配置数量的组主数据
- 默认全局配置
- 初始年份状态记录

### 6.3 配置管理

推荐配置项包括：

- 监听端口
- 数据库连接
- JWT 或统一认证接入参数
- 日志级别
- OpenAPI 开关
- 自动保存间隔（如需后端兜底）
- 当前规则版本、模板版本

---

## 7. OpenAPI 与接口文档

- 推荐接入 `swaggo` 自动生成接口文档。
- 每个 Handler 方法应补接口注释，至少说明：
  - 用途
  - 权限
  - 关键入参
  - 关键失败场景
- 自动文档不替代 `docs/api_design.md`。
- 若接口语义有变化，必须先改正式接口文档，再改代码。

## 8. 常用命令建议

```bash
# 拉起本地服务
make run

# 执行测试
make test

# 执行数据库迁移
make migrate-up

# 回滚最近一次迁移
make migrate-down

# 生成 OpenAPI 文档
make swagger
```

说明：

- 若项目初期未配置 `Makefile`，至少要在 `docs/README.md` 或本文件追加等价命令。
- 命令名称可随项目骨架调整，但职责应保持不变。

## 9. 开发清单（每次改动前后）

改动前：

1. 明确本次改动影响的业务域。
2. 确认是否影响状态机、规则口径、接口结构、表结构。
3. 若影响规则或字段映射，先改文档再写代码。

改动后：

1. 编译通过。
2. 受影响接口 `.http` 冒烟通过。
3. 关键规则具备自动化测试或手工回归记录。
4. 文档同步更新。
5. 未引入与正式需求相冲突的实现捷径。
