## 2. 核心判断

### 2.1 当前项目的真正复杂度

这个项目的难点不在高并发，也不在海量数据，而在：

- Excel 规则可维护
- 年份 / 阶段 / 财报 / 破产 / 异常解锁的状态一致性
- 管理员与玩家操作边界清晰
- 汇总口径不被异常流程破坏

因此本项目的技术选型优先级应为：

`规则正确 > 状态稳定 > 可维护性 > 开发效率 > 性能冗余`

### 2.2 当前推荐的总体方案

首版推荐采用：

`Go 单体后端 + MySQL + 前后端分离 Web 前端 + 业务字段存储 + Excel 风格页面映射`

这意味着：

- 不做微服务
- 不做通用工作流平台
- 不把 Excel 当运行引擎
- 不按 Excel 单元格直接建模成数据库
- 不引入重型电子表格引擎作为核心业务底座

## 3. 为什么技术选型现在就能做

### 3.1 不依赖 Excel 细部标签即可冻结的部分

以下内容现在就可以确定，并且已经在当前仓库冻结为首版基线：

- 后端是否用 Go
- 是否做单体服务
- 是否做前后端分离
- 状态机是否独立建模
- 数据是按业务字段存还是按单元格存
- 是否做规则计算模块分层
- 是否做日志 / 审计 / 异常解锁记录
- 是否用自定义 Excel 风格页面而不是通用电子表格引擎

### 3.2 仍需结合当前冻结 Excel 继续收口的部分

以下内容已经有当前冻结基线，但仍需随着页面和文档收口继续核对：

- 字段最终显示名称
- 字段到页面位置的最终映射
- 绿色手工格的最终命名口径
- 公式来源注释中的最终单元格引用
- API 字段命名和数据库字段命名的最终落地文本

### 3.3 需要重新评估技术方案的变化边界

如果 Excel 后续变化仅是名称调整或小公式调整，通常不需要推翻技术方案。

但如果 Excel 变化影响以下内容，则需要回到技术评估：

- 年份 / 阶段流程改变
- 财报结构改变
- 汇总口径改变
- 跨年联动方式改变
- 手工输入边界大幅变化

## 4. 总体架构推荐

### 4.1 架构形态

推荐：`前后端分离 + 单体后端服务`

| 层 | 推荐方案 | 说明 |
|---|---|---|
| 前端 | Web SPA | 负责 Excel 风格页面、交互、校验提示、调用 API |
| 后端 | Go 单体 API 服务 | 负责权限、状态机、规则计算、持久化、汇总 |
| 数据库 | MySQL 8.x | 负责业务数据、状态、日志、汇总快照 |
| 文件来源 | Excel / Word 源文件仅作为规则依据 | 不作为系统运行时引擎 |

### 4.2 为什么不推荐微服务

首版不推荐微服务，原因如下：

- 用户规模小：`10 个组 + 1 个管理员`
- 并发量低，不需要拆分服务解决性能问题
- 当前主要风险在业务规则和状态一致性，不在服务拆分
- 微服务会显著增加：
  - 部署成本
  - 调试成本
  - 跨服务事务与状态同步复杂度

### 4.3 为什么不推荐工作流引擎

虽然系统存在阶段流转，但当前流转模式是有限、明确、可枚举的。

因此不推荐首版引入通用工作流引擎，原因如下：

- 状态机已足够清晰
- 工作流引擎会放大实现复杂度
- 游戏规则变动主要集中在业务计算和流程边界，不是审批链编排

## 5. Go 后端技术选型建议

### 5.1 推荐目标

Go 后端应优先满足：

- 状态流转清晰
- 规则实现集中
- 审计日志清楚
- API 边界稳定
- 便于后续 Excel 小调整时维护

### 5.2 推荐基础组合

若团队没有强制指定公司内 Go 基座，首版推荐组合如下：

| 维度 | 推荐 | 说明 |
|---|---|---|
| HTTP 框架 | `Gin` | 生态成熟，足够轻，适合首版单体 API |
| 配置管理 | `Viper` 或等价配置方案 | 适合多环境配置 |
| 日志 | `Zap` | 结构化日志清晰，便于排查提交流程 |
| 参数校验 | `go-playground/validator` | 适合请求参数校验 |
| OpenAPI | `swaggo/swag` 或等价方案 | 用于接口文档生成 |
| 数据库驱动 | MySQL 官方驱动 | 稳定、通用 |
| ORM / 数据访问 | `GORM` 为首版推荐；团队若更偏 SQL 明确控制，可选 `sqlx/sqlc` | 首版更看重交付效率与迭代速度 |
| 数据库迁移 | `golang-migrate` 或等价方案 | 保证结构变更可追踪 |
| 测试 | `testing + testify + httptest` | 足以覆盖首版 API 和规则测试 |

### 5.3 如果公司已有 Go 基座

若公司已有成熟 Go 脚手架，并且已包含以下能力，优先复用：

- 登录认证
- 权限中间件
- 配置中心
- 日志链路
- 统一错误响应
- 数据库访问封装
- OpenAPI 文档生成

但复用前必须确认：

- 不会强迫项目采用不适合的重型架构
- 不会把状态机逻辑塞进过度抽象的通用流程层
- 不会把 Excel 风格业务页强行改成普通 CRUD 后台页面

## 6. 前端技术方向建议

### 6.1 当前推荐方向

前端推荐保持：`Vue 3 + TypeScript + Vite` 的单页应用方向。

原因：

- 适合高交互表格页面
- 适合玩家端 / 管理端双端页面共存
- 适合 Excel 风格高保真 UI 实现
- 适合与 Go API 做清晰分层

### 6.2 页面实现原则

首版前端不推荐把完整电子表格引擎作为核心底座。

推荐做法：

- 用自定义页面结构还原 Excel 风格
- 页面数据绑定到业务字段
- 锁定态、已提交态、未来阶段态由业务状态控制
- 公式计算仍由后端规则层负责，前端只做展示和必要前置校验

### 6.3 为什么不推荐直接接入通用电子表格引擎

例如 Luckysheet / Univer / Handsontable 这类库，首版不建议直接作为核心业务底层。

原因：

- 会诱导系统按“单元格”建模，而非按业务字段建模
- 状态机、权限、阶段锁定、异常解锁会被电子表格模型干扰
- 后续规则变更时，维护点容易分散在前端表格配置中

结论：

- 可以借鉴其交互风格
- 不应让其主导业务数据模型

## 7. 数据存储策略建议

### 7.1 总体建议

不推荐两种极端：

- 极端一：所有字段拆成数据库独立列
- 极端二：所有数据都按 Excel 单元格坐标存 JSON

首版推荐：`关系型主模型 + 分区块业务 JSON + 汇总快照`

### 7.2 推荐存储分层

| 数据类型 | 推荐存储方式 | 说明 |
|---|---|---|
| 组、用户、年份配置、状态 | 关系型字段 | 用于稳定查询与状态控制 |
| 经营页手工输入区 | 按业务区块存 JSON / 结构体映射 | 适应 Excel 小调整，避免列爆炸 |
| 财报页手工输入区 | 按业务区块存 JSON / 结构体映射 | 保持灵活性 |
| 关键计算结果 | 关系型字段或快照表 | 便于汇总与排名查询 |
| 提交记录 / 解锁记录 / 操作日志 | 独立日志表 | 便于审计 |

### 7.3 这样设计的原因

- 状态和关键结果适合强结构化
- 手工输入区会受 Excel 调整影响，适合相对灵活的区块结构
- 汇总查询不能完全依赖运行时实时重算，需有可追踪快照

## 8. 规则实现策略建议

### 8.1 规则层必须独立

后端必须显式划分一个 `规则计算层`，不要把规则散落在：

- Controller
- HTTP Handler
- ORM Hook
- 前端页面脚本

### 8.2 推荐分层方式

| 层 | 职责 |
|---|---|
| Handler / Controller | 参数校验、调用应用服务、返回响应 |
| Application Service | 处理提交动作、状态推进、事务边界 |
| Domain / Rule Service | 经营规则计算、财报规则计算、季末现金展示计算、破产判定 |
| Repository | 数据持久化 |

### 8.3 Excel 变化的承接方式

推荐把规则拆成两部分：

1. `代码层规则`
- 真正的计算逻辑
- 状态判断
- 提交校验

2. `映射层配置`
- 字段显示名称
- 页面位置映射
- Excel 来源说明
- 规则版本标识

这样当 Excel 小改时：

- 如果只是名称变化，优先改映射层
- 如果是口径变化，再改规则代码

### 8.4 是否需要规则版本号

推荐需要。

首版建议至少预留：

- `rule_version`
- `template_version`

目的：

- 标识当前系统基于哪一版 Excel 规则
- 后续若有小改版，可追踪差异来源

## 9. 状态机落地建议

### 9.1 状态必须显式存储

不建议通过“看哪些字段有没有值”来隐式推导状态。

推荐显式存储：

- 年份主状态
- 当前经营阶段
- 财报状态
- 组级破产标记

### 9.2 原因

如果状态不显式存储，会在以下场景出问题：

- 异常解锁后状态回收
- 汇总撤回与重算
- 管理员查看组数据时的状态判断
- 前端锁定区控制

### 9.3 提交与状态推进关系

推荐所有正式提交都显式记录：

- 提交动作类型
- 提交前状态
- 提交后状态
- 提交人
- 提交时间
- 关键校验结果

## 10. API 设计建议（Go 版承接）

### 10.1 总体风格

虽然参考文档中的 RDPM 是 Java 体系，但本项目仍建议沿用“动作式接口 + 明确业务动作”的风格。

原因：

- 该项目本质上有很多强业务动作
- 如：
  - 阶段提交
  - 财报提交
  - 开放下一年
  - 异常解锁
  - 录入初始基线
- 单纯资源式 REST 容易把动作语义写薄

### 10.2 推荐接口域划分

| 域 | 说明 |
|---|---|
| `auth` | 登录、当前用户信息 |
| `game-config` | 最终年份、规则版本、基础配置 |
| `player-operating` | 玩家经营页读取、草稿保存、阶段提交 |
| `player-report` | 财报读取、财报提交 |
| `admin-summary` | 汇总页、最终排名 |
| `admin-control` | 开放下一年、初始基线、异常解锁 |
| `admin-group-data` | 查看任一组任一年数据 |
| `audit-log` | 提交日志、异常解锁日志 |

### 10.3 错误状态语义

推荐延续参考规范中的 REST 语义：

- `400`：参数错误
- `401`：未登录
- `403`：无权限
- `404`：资源不存在
- `409`：状态冲突
- `422`：业务规则不满足
- `500`：系统异常

对于本项目，尤其要用好：

- `409`：例如重复推进、状态已变化
- `422`：例如当前阶段必填项未完成、财报平衡失败、未到开放阶段

## 11. 数据库设计方向建议

### 11.1 推荐数据库

推荐：`MySQL 8.x`

原因：

- 团队普遍熟悉度高
- 适合首版单体应用
- 足以支持当前规模和复杂度

### 11.2 表设计原则

推荐至少包含以下几类表：

| 类型 | 说明 |
|---|---|
| 基础表 | 用户、组、基础配置 |
| 年份状态表 | 记录 `组 + 年` 的主状态与当前阶段 |
| 经营数据表 | 存储经营页区块数据 |
| 财报数据表 | 存储财报手工项与计算结果快照 |
| 汇总快照表 | 存储正式年份汇总结果 |
| 审计日志表 | 存储提交、异常解锁、管理员动作 |

### 11.3 不建议的数据库做法

- 不建议把所有表单字段都摊平成超大宽表
- 不建议完全不做快照，所有汇总都实时重算
- 不建议依赖前端传来的计算结果直接入库为准

## 13. 当前推荐结论

### 13.1 推荐方案

当前首版推荐技术方案为：

`Go 单体后端 + MySQL + Vue 3/TypeScript 前端 + 自定义 Excel 风格页面 + 业务字段建模 + 独立规则层 + 显式状态机`

### 13.2 不推荐方案

当前不推荐：

- 微服务
- 工作流引擎
- 以通用电子表格引擎作为核心底座
- 按 Excel 单元格直接建模存储
- 前端实时主导公式计算

### 13.3 当前已冻结的外部规则基线

- `game doc/1组 最终版.xlsx` 已作为当前公式与显示名称冻结基线

当前这项主要用于：

- 字段命名映射收口
- 页面标签与帮助文案核对
- 规则来源注释追溯

不再作为当前技术选型与开发排期的阻塞项。
