# 管理员操作年份收口方案

## 1. 背景

管理员端当前存在三个容易造成“年份口径混乱”的入口：

1. `回退与修正 -> 退回重提` 允许管理员手动填写年份。
2. `回退与修正 -> 恢复快照` 恢复前需要填写恢复原因和确认文本，现场操作偏重。
3. `通知与奖惩 -> 奖惩下发区` 允许管理员通过年份下拉把奖惩写入历史年份。

用户已确认新的业务口径：

- 退回重提的年份不再由管理员自由填写，而是取目标小组当前所在填写年份。
- 跨年纠错通过单组快照恢复处理，不通过普通退回重提手工指定历史年份。
- 恢复快照不再要求管理员填写原因和确认文本；系统自动记录默认原因。
- 奖惩下发的年份和阶段都由目标小组当前状态决定，管理员不能在后续年份把奖惩写回历史年份。

## 2. 核心定义

### 2.1 当前小组所在填写年份

系统按以下顺序解析目标小组的当前操作年份：

1. 如果目标小组存在 `rollback_pending = true` 的年份，取最早的待重提年份。
2. 否则取全局 `currentOpenYear`。

示例：

- 当前开放年份为 `2年`，第二组没有待重提状态，则第二组当前操作年份为 `2年`。
- 当前开放年份为 `2年`，第二组通过快照恢复到 `1年 Q2`，则第二组 `1年` 和后续受影响年份处于待重提链路，当前操作年份取 `1年`。

### 2.2 管理员操作上下文

前端不再自行推断年份，而是从后端读取目标小组的管理员操作上下文。上下文至少包含：

- 目标小组
- 全局当前开放年份
- 当前小组所在填写年份
- 年份主状态
- 经营阶段状态
- 财报状态
- 是否处于待重提
- 奖惩可归属阶段
- 当前是否允许下发奖惩
- 当前是否允许执行退回重提
- 不允许操作时的原因说明

该上下文用于页面展示，但不作为最终信任来源。退回重提和奖惩接口在提交时仍必须由后端重新解析并校验。

## 3. 退回重提方案

### 3.1 页面口径

- 管理员只选择目标小组、目标类型和经营阶段。
- 年份字段改为只读展示，值来自目标小组当前操作上下文。
- 页面文案明确：普通退回重提适合当前操作年份内修正；跨年修正请使用恢复快照。

### 3.2 后端口径

- `yearNo` 字段可继续保留用于兼容旧调用，但不能作为管理员自由输入的权威来源。
- 服务端处理退回重提时重新解析目标小组当前操作年份。
- 如果请求传入 `yearNo` 且与服务端解析年份不一致，返回业务错误，不执行退回。
- 如果请求未传 `yearNo`，服务端直接使用解析出的当前操作年份。
- 原有“目标阶段必须已正式提交”“下一年已开放后不允许普通跨年退回”等业务校验继续保留。

### 3.3 边界

- 普通退回重提不负责跨年恢复历史节点。
- 若小组已经通过快照恢复处于待重提链路，当前操作年份会指向待重提目标年，管理员后续普通退回仍围绕该目标链路处理，不能再手工指定另一个历史年份。

## 4. 恢复快照方案

### 4.1 页面口径

- 快照列表、筛选、详情继续保留。
- 删除“恢复原因”输入框。
- 删除“确认文本”输入框。
- 恢复按钮点击后直接执行恢复；按钮仍保留危险样式和快照不可恢复禁用态。

### 4.2 后端口径

- 恢复快照接口不再校验确认文本。
- 恢复原因为空时，服务端自动写入默认原因 `管理员恢复快照`。
- 安全快照、回退日志、失效草稿、汇总撤回、奖惩有效状态按快照时点恢复、订单交付失效等原有安全逻辑全部保留。

### 4.3 边界

- 取消原因和确认文本只降低现场操作成本，不取消审计。
- 审计记录中的原因由系统默认值补齐，后续仍可通过回退日志追溯是谁在什么时间恢复了哪个快照。

## 5. 通知与奖惩方案

### 5.1 页面口径

- 普通通知不受影响，仍可全体或单组发送自由文本。
- 奖惩下发区只允许管理员选择目标小组、类型、金额、原因。
- 年份下拉删除，改为只读展示目标小组当前操作年份。
- 阶段继续只读展示系统自动归属结果：
  - `Q1_OPEN -> Q1`
  - `Q2_OPEN -> Q2`
  - `Q3_OPEN -> Q3`
  - `Q4_OPEN -> Q4`
  - `YEAR_END_OPEN -> YEAR_END`
  - 财报开放且未正式提交时归属 `YEAR_END`
- 若目标小组当前不能下发奖惩，页面展示阻断原因。

### 5.2 后端口径

- 奖惩下发和奖惩预览在创建奖惩时，服务端必须重新解析目标小组当前操作年份。
- 如果请求传入 `yearNo` 且与服务端解析年份不一致，返回业务错误，不执行预览或下发。
- 如果请求未传 `yearNo`，服务端直接使用解析出的当前操作年份。
- 阶段继续由现有服务端状态解析器决定，管理员不能通过请求覆盖。
- 作废奖惩仍按原奖惩记录归属年份和当前状态校验，不改成手动年份。

### 5.3 边界

- 不能在 `2年` 时手动给某组下发 `1年` 奖惩。
- 若确实发现历史奖惩录入错误，应通过“作废奖惩”处理；若历史阶段已经锁定，先通过回退与修正让该组回到可编辑链路。

## 6. 验收点

1. 退回重提页面选择小组后，年份只读显示，不再出现可输入年份框。
2. 手工调用退回重提接口传入非当前操作年份时，后端拒绝。
3. 恢复快照详情页不再出现恢复原因和确认文本输入框。
4. 手工调用恢复快照接口仅传 `snapshotId` 可成功；日志原因自动记录为 `管理员恢复快照`。
5. 通知与奖惩页面奖惩下发区不再出现年份下拉框。
6. 选择不同小组时，奖惩下发区刷新显示该组当前操作年份和系统归属阶段。
7. 手工调用奖惩预览或下发接口传入历史年份时，后端拒绝。
8. 已完成财报、年份完成或已破产小组仍不能直接下发奖惩。

## 7. 本轮不做

- 不新增全局快照恢复。
- 不允许普通退回重提自由跨年。
- 不改变订单模块的快照边界。
- 不改变奖惩计算公式。
- 不改变普通通知功能。
