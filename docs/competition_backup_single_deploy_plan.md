# 场景 B 数据备份与单实例新目录部署方案

> 更新日期：2026-08-03
> 适用场景：管理员电脑已经跑过一次比赛，旧比赛数据不能清空；需要把最新代码部署到管理员电脑，并将后续正式部署收口为“一套系统 + 网页内选择版本包”。
> 文档定位：本文件是开发前的确认方案，不是已经完成的脚本说明。真正脚本落地后，再同步更新现场部署清单和管理员操作手册。

## 1. 当前确认结论

本轮部署方案按以下口径收口：

1. 管理员电脑已有旧比赛数据时，先备份旧数据库，再部署新代码。
2. 备份脚本由管理员输入文件名，脚本在当前部署目录下自动创建或复用 `backup` 文件夹。
3. 备份产物生成 `zip` 文件，文件名以管理员输入为主；同名不覆盖，自动追加时间戳。
4. 备份 `zip` 中第一版至少包含完整数据库 SQL、备份说明、结果摘要 CSV。
5. 新代码部署到新的文件夹，不覆盖旧代码目录。
6. 新部署方向收口为单实例：一个正式包、一个启动入口、一个数据库、一个访问地址。
7. 生产制造版 / 贵宾服务版不再通过“启动哪个脚本”区分，而是在网页赛前配置页选择版本包。
8. 已有旧数据库备份后可留作归档；若后续要精确追溯，应恢复到临时数据库读取。
9. 当前工作区原存在未跟踪空文件 `frontend/npm.cmd`，开发落地时按已确认口径删除，避免影响正式打包。
10. 正式打包脚本需要包含 `migrations/mysql/0017_order_delivery_revenue.sql`，否则新部署包会缺订单交付自动写销售收入相关迁移。

## 3. 为什么选择“新文件夹部署”

当前管理员电脑不是空机器，而是已经存在：

- 上一次比赛数据；
- 上一次比赛使用的旧代码；
- 旧配置、旧启动脚本、旧数据库；
- 与当前最新代码不完全一致的数据库结构和功能口径。

因此直接覆盖旧代码目录风险较高。推荐采用：

```text
旧目录：原样保留，不覆盖
旧数据库：先备份，作为上一场比赛归档
新目录：解压最新部署包
新数据库：用于下一场比赛
```

### 3.1 与“覆盖旧目录”的对比

| 方案 | 优点 | 风险 / 缺点 | 结论 |
|---|---|---|---|
| 覆盖旧代码目录 | 路径少，看起来简单 | 旧脚本、旧配置、新代码可能混在一起；一旦新系统启动失败，旧系统也难回退；可能误升级旧数据库结构 | 不推荐用于本次场景 B |
| 新文件夹部署 | 旧比赛留档清楚；新旧系统互不污染；失败时可回头看旧目录 | 管理员电脑上短期有两个系统目录，需要命名清楚；端口可能冲突 | 推荐 |

最终判断：

```text
本次采用“新文件夹部署 + 新数据库 + 旧库先备份”的稳妥方案。
```

## 4. 推荐目录结构

示例目录如下：

```text
E:\deploy\
  ├─ sandbox-game-shengchan-old\
  │   ├─ 旧版系统文件
  │   └─ backup\
  │       └─ 上一次比赛数据.zip
  │
  └─ sandbox-game-competition\
      ├─ bin\
      ├─ configs\
      ├─ frontend\
      ├─ migrations\
      ├─ scripts\
      ├─ backup\
      │   └─ 新比赛备份.zip
      ├─ 启动沙盘系统.bat
      ├─ 重启沙盘系统.bat
      ├─ 停止沙盘系统.bat
      ├─ 备份当前比赛数据库.bat
      └─ 赛前重置当前比赛.bat
```

实际落地时不强制改名旧目录，原则是：

- 旧目录不要覆盖；
- 新目录名称要清楚；
- 管理员以后只使用新目录里的启动入口；
- 旧目录只作为上一场比赛留档。

## 5. 单实例部署口径

新部署推荐收口为单实例：

```text
一套代码
一个配置文件
一个数据库
一个端口
一个访问地址
一个启动入口
```

版本选择不再由启动脚本决定，而由系统内版本包决定：

```text
管理员打开系统
  ↓
进入赛前配置页
  ↓
选择生产制造版 / 贵宾服务版
  ↓
初始化后版本锁定
```

### 5.1 为什么不再区分“启动制造业版 / 启动服务版”

当前系统已经有版本包机制：

- `PRODUCTION_V1`：生产制造版；
- `VIP_SERVICE_V1`：贵宾服务版；
- 后续也可继续扩展其他版本。

因此业务版本不应再由不同分支或不同启动脚本承担。更合理的产品口径是：

```text
脚本只负责启动系统；
版本由网页赛前配置页选择。
```

这样管理员不需要判断自己应该启动哪一个脚本，减少现场操作错误。

### 5.2 单实例的边界

单实例适用于：

- 管理员电脑同一时间只服务一场比赛；
- 旧比赛只需要备份留档；
- 新比赛使用新数据库重新初始化；
- 管理员希望一个入口完成启动和使用。

如果未来确实需要同一台电脑同时运行两场比赛，仍可用同一套代码加两个 yaml 跑两个实例。但这属于高级部署模式，不作为当前推荐口径。

## 6. 场景 B 标准流程

推荐现场执行顺序：

```text
第一步：停止旧系统
  ↓
第二步：在旧系统目录执行备份脚本
  ↓
第三步：确认 backup 目录下生成 zip 文件
  ↓
第四步：新建一个新部署目录
  ↓
第五步：把最新版本包解压到新部署目录
  ↓
第六步：配置新的 configs\competition.yaml
  ↓
第七步：初始化新数据库
  ↓
第八步：启动新系统
  ↓
第九步：管理员打开新地址
  ↓
第十步：管理员在赛前配置页选择本场比赛版本包
```

关键禁止事项：

- 不直接覆盖旧系统目录；
- 不在未备份前重置旧数据库；
- 不把旧比赛数据库直接当作新比赛数据库继续使用；
- 不通过两个启动脚本让管理员选择制造业版或服务版。

## 7. 数据库备份脚本方案

### 7.1 管理员使用方式

管理员执行：

```text
备份当前比赛数据库.bat
```

脚本提示：

```text
请输入备份文件名：
```

管理员输入：

```text
第一场正式比赛数据
```

脚本自动生成：

```text
当前部署目录\backup\第一场正式比赛数据.zip
```

如果 `backup` 文件夹不存在，则自动创建；如果已经存在，则直接复用。

### 7.2 文件名规则

管理员输入的是“主文件名”，脚本自动处理：

- 自动补 `.zip` 后缀；
- 自动清理 Windows 非法字符：`\ / : * ? " < > |`；
- 同名文件不覆盖，自动追加时间戳。

示例：

```text
输入：第一场正式比赛数据
生成：backup\第一场正式比赛数据.zip

如果已存在：
生成：backup\第一场正式比赛数据_20260803_153000.zip
```

### 7.3 zip 内容

第一版备份 zip 建议包含：

```text
第一场正式比赛数据.zip
  ├─ 第一场正式比赛数据.sql
  ├─ 第一场正式比赛数据_结果摘要.csv
  └─ 第一场正式比赛数据_备份说明.txt
```

其中：

- `.sql` 是完整数据库备份，包含表结构和所有数据；
- `_结果摘要.csv` 是轻量比赛结果摘要；
- `_备份说明.txt` 记录备份时间、数据库名、配置路径、代码基线、注意事项。

### 7.4 完整数据库备份口径

备份脚本应读取当前部署目录的：

```text
configs\competition.yaml
```

并解析其中的 MySQL DSN，调用 `mysqldump` 导出完整数据库。

推荐实现要求：

- 优先从系统 `PATH` 查找 `mysqldump.exe`；
- 找不到时尝试常见 MySQL / MariaDB 安装路径；
- 找不到时给出明确提示，不静默失败；
- 不在控制台打印数据库密码；
- 建议使用临时 `defaults-extra-file` 传递账号密码，执行后删除临时文件；
- 使用 `--single-transaction` 降低备份期间锁表风险；
- 使用 `--default-character-set=utf8mb4` 保证中文内容正常导出。

### 7.5 摘要生成失败时的处理

数据库备份是底线，结果摘要是附加文件。推荐规则：

```text
如果 SQL 备份失败：
  整个备份失败，不生成成功提示。

如果 SQL 备份成功，但结果摘要生成失败：
  仍然生成 zip。
  zip 中包含 SQL 和备份说明。
  备份说明中记录“结果摘要生成失败”。
  控制台提示管理员：数据库已备份成功，但摘要生成失败。
```

这样不会因为摘要问题影响旧比赛数据保全。

## 8. 结果摘要 CSV 方案

第一版结果摘要只做轻量版，不做复杂 Excel 报表。

### 8.1 第一版包含字段

建议字段如下：

| 字段 | 来源口径 | 说明 |
|---|---|---|
| 小组编号 | `sg_group.group_no` | 第几组 |
| 小组名称 | `sg_group.group_name` | 小组显示名 |
| 当前经营状态 | `sg_group.business_status` | 当前状态优先，不读旧快照状态 |
| 最终有效年份 | 当前比赛最终年，或该组最后一个有效汇总年份 | 用于识别未完成 / 破产情况 |
| 销售收入 | 有效汇总快照或对应财报计算结果 | 优先与管理员汇总页一致 |
| 净利润 | 有效汇总快照或对应财报计算结果 | 优先与管理员汇总页一致 |
| 所有者权益 | 有效汇总快照或对应财报计算结果 | 排名依据通常来自权益 |
| 最佳 CEO 得分 | 有效财报提交快照的计算 JSON | 读取 `reportBestCeoScore` |
| 最佳 CFO 得分 | 有效财报提交快照的计算 JSON | 读取 `reportBestCfoScore` |
| 最佳销售总监得分 | 有效财报提交快照的计算 JSON | 读取 `reportBestSalesDirectorScore` |
| 最佳市场经营总监得分 | 有效财报提交快照的计算 JSON | 读取 `reportBestMarketDirectorScore` |
| 最佳科技创新总监得分 | 有效财报提交快照的计算 JSON | 读取 `reportBestTechnologyDirectorScore` |
| 最佳生产/服务人力总监得分 | 财报手工项或计算展示口径 | 生产制造版显示“生产人力”，贵宾服务版显示“服务人力” |
| 企业认证得分 | 财报手工项 | 只作为摘要展示 |
| 排名 | 管理员最终排名口径 | 优先读取最终年有效汇总排序，不临时自定义排名 |

### 8.2 数据来源优先级

为了避免把失效草稿或旧提交误当正式结果，第一版摘要按以下优先级读取：

1. 排名、收入、利润、权益优先读取 `sg_group_summary_snapshot` 中 `summary_effective = 1` 的有效汇总快照。
2. CEO / CFO / 总监分优先读取有效汇总快照对应的 `source_report_submit_version`，再关联 `sg_group_report_submission.report_computed_snapshot_json`。
3. 如果对应提交流水缺失，再降级读取 `sg_group_report.report_computed_payload_json`，并在备份说明中记录“摘要存在降级读取”。
4. 待重提、回退失效、未完成小组不得伪造成有效排名，应在摘要中明确显示状态。

### 8.3 CSV 而不是 XLSX

第一版建议输出 CSV：

- Excel 可直接打开；
- 不依赖复杂 Excel 生成库；
- 更适合作为备份脚本的一部分；
- 便于后续自动化校验。

暂不做：

- 多 sheet；
- 合并单元格；
- 样式；
- 公式；
- 订单、奖惩、快照全量审计表。

如果后续管理员需要更正式的成绩单，再单独升级为 `xlsx` 导出。

## 9. 旧备份 zip 后续如何读取

备份 zip 可以支持两种读取方式。

### 9.1 快速查看

如果只需要看：

- 每组结果；
- 最终排名；
- 最终年份收入、利润、权益；
- CEO / CFO / 各总监得分；
- 是否破产 / 待重提；

可以直接读取 zip 中的 `_结果摘要.csv`。

### 9.2 精确追溯

如果需要分析：

- 某个得分为什么是这个值；
- 某年某季度数据如何影响最终结果；
- 订单交付、回退、快照、奖罚是否影响结果；
- 失效草稿是否被错误计入；

应将 zip 中 `.sql` 恢复到临时数据库，再按真实表结构查询。

结论：

```text
结果摘要用于快速看；
完整 SQL 用于严肃追溯。
```

## 10. 正式包打包脚本调整点

当前已确认正式包需要包含：

```text
migrations\mysql\0017_order_delivery_revenue.sql
```

原因：

- `cmd/dbtool/main.go` 已经会执行 `0017_order_delivery_revenue.sql`；
- 如果打包脚本不复制该文件，部署包里的 dbtool 会在初始化或迁移时找不到 SQL 文件；
- 该迁移与订单交付自动写销售收入的修订历史表有关。

后续开发时需要保留此修正。

## 11. `frontend/npm.cmd` 空文件处理

当前工作区存在未跟踪空文件：

```text
frontend\npm.cmd
```

该文件不是正式源码的一部分，且可能影响前端构建：

```text
进入 frontend 目录
执行 npm.cmd run build
  ↓
Windows 可能优先命中当前目录下 0 字节 npm.cmd
  ↓
构建失败
```

用户已确认采用方案 A：

```text
删除 frontend\npm.cmd 空文件。
```

该动作已纳入 D1 ~ D12 开发落地范围。

## 13. 验收口径

第一版开发完成后，至少按以下项验收：

1. 正式打包产物包含 `migrations/mysql/0017_order_delivery_revenue.sql`。
2. 正式打包产物包含数据库备份脚本和管理员双击入口。
3. 在部署目录执行备份入口，能提示管理员输入文件名。
4. 未存在 `backup` 文件夹时，脚本能自动创建。
5. 已存在 `backup` 文件夹时，脚本能直接复用。
6. 输入普通中文文件名后，能生成对应 zip。
7. 输入非法文件名字符时，脚本能自动替换为安全文件名。
8. 同名 zip 已存在时，脚本不覆盖旧文件，自动追加时间戳。
9. zip 中包含完整 SQL。
10. zip 中包含备份说明 TXT。
11. zip 中包含结果摘要 CSV。
12. CSV 能用 Excel 打开，中文列名不乱码。
13. CSV 排名 / 收入 / 利润 / 权益与管理员汇总页一致。
14. CSV CEO / CFO / 总监分来自有效财报提交结果，不读取失效草稿。
15. SQL 备份失败时，脚本明确失败，不提示备份成功。
16. 摘要生成失败但 SQL 成功时，zip 仍保留 SQL，并在说明中记录摘要失败。
17. 新部署目录不覆盖旧部署目录。
18. 新部署入口只有一个“启动沙盘系统”，版本由网页赛前配置页选择。

## 15. 最终判断

本方案推荐采用：

```text
先备份旧库
  ↓
旧代码目录原样保留
  ↓
新代码部署到新目录
  ↓
新比赛使用新数据库
  ↓
新系统收口为单实例
  ↓
版本在网页赛前配置页选择
```

这条路线的核心优点是稳：

- 旧比赛数据有完整 SQL 备份；
- 管理员能直接看到结果摘要；
- 新旧代码不会互相覆盖；
- 新旧数据库不会互相污染；
- 后续管理员只需要面对一个启动入口；
- 版本包机制真正承担生产制造版 / 贵宾服务版差异。

因此，本方案可作为后续开发备份脚本、单实例部署入口和正式部署手册更新的依据。
