# 沙盘经营系统服务版正式比赛上线方案（首版）

> 更新日期：2026-04-03  
> 适用方式：基于《正式需求文档（首版）》《技术选型细化文档（Go 方向）》《联调与人工验收运行手册（首版）》与当前项目实现状态，定义首版正式比赛的推荐部署方式、环境边界、部署步骤与现场保障口径。  
> 文档定位：本文件回答“正式比赛时系统应该部署在哪里、用户访问什么地址、赛前要准备什么、现场如何保障稳定运行”。

## 1. 目标

首版正式比赛上线方案需要解决四件事：

1. 让 `10` 个玩家组账号和 `1` 个管理员账号访问同一套正式比赛系统，而不是访问开发人员本机开发环境。
2. 让前端页面与后端 API 以正式服务方式运行，不依赖 `Vite` 开发服务器长期支撑比赛现场。
3. 让正式比赛数据与开发库、演练库彻底隔离，避免测试行为污染比赛结果。
4. 让现场主持人、开发与管理员知道比赛前、比赛中、比赛后的最小操作口径。

---

## 2. 推荐上线形态

首版正式比赛推荐采用以下形态：

- 一台专用 `比赛主机`
- 一套专用 `正式比赛数据库`
- 一个统一访问地址
- 前端打包为静态资源
- `Nginx` 提供统一访问入口与静态页面
- Go 服务提供业务 API

推荐访问形式：

- `http://<比赛主机IP>`
- `http://sandbox-game.company.local` （若公司内网支持固定域名）

正式比赛时，玩家与管理员都不应再访问：

- 开发者个人电脑的临时地址
- `http://127.0.0.1:5173`
- `http://localhost:5173`
- 依赖开发终端常驻的 `Vite` 页面地址

---

## 3. 环境分层建议

| 环境 | 用途 | 是否允许写入 | 是否用于正式比赛 |
|---|---|---|---|
| 开发环境 | 开发、自测、调试 | 是 | 否 |
| 多组演练环境 | 主持人彩排、联调、流程验收 | 是 | 否 |
| 单组演练环境 | 单链路推演、公式回归、快速验证 | 是 | 否 |
| 正式比赛环境 | 正式比赛当天使用 | 是 | 是 |

正式比赛环境必须满足：

- 独立数据库
- 独立配置文件
- 独立账号与初始化数据
- 不与开发环境共用进程或数据

若现场同时保留“制造业版”和当前 `guibing` 服务版，两套系统还必须继续满足：

- 不共用同一个 MySQL 数据库
- 不共用同一份 `competition.yaml`
- 不混用同一个正式上线包目录

推荐命名口径：

| 游戏版本 | 建议正式库名 | 建议上线包目录名 |
|---|---|---|
| 制造业版 | `sandbox_game_competition` | `sandbox-game-competition` |
| 服务版（`guibing`） | `sandbox_game_service_competition` | `sandbox-game-service-competition` |

---

## 4. 比赛主机建议

比赛主机建议承担以下职责：

- 承载 Go 后端正式服务
- 承载 `Nginx`
- 承载前端打包后的静态资源
- 连接正式比赛数据库
- 对局域网内所有参赛电脑提供统一访问入口

比赛主机建议满足：

- 接入稳定电源
- 接入稳定局域网
- 使用固定内网 IP
- 比赛期间不再进行开发、改代码、热更新
- 关闭与比赛无关的软件和大流量下载任务

推荐网络口径：

- 玩家电脑、管理员电脑、比赛主机位于同一局域网
- 对浏览器开放的端口统一为 `80` 或 `8080`
- 数据库端口不对普通玩家电脑开放

---

## 5. 部署口径

首版推荐的部署结构如下：

1. 前端执行 `build`，产出 `dist`
2. `Nginx` 提供前端 `dist` 与统一访问地址
3. Go 后端读取正式比赛配置启动，仅提供 `/api/v1/sandbox-game/*` 接口
4. MySQL 使用正式比赛库

对现场参赛人员来说，应该感知为：

- 所有人只访问一个地址
- 登录后按角色自动跳转
- 不感知前后端分离细节

---

## 6. 当前仓库与正式比赛的差距

截至 `2026-04-01`，当前仓库的开发主链仍以本地联调模式为主：

- 前端开发服务：`5173`
- 后端 API：`8080`

这说明当前项目已适合开发、联调、验收，但在正式比赛前，仍建议补上以下收口项：

- 正式比赛配置文件
- 正式比赛数据库初始化脚本
- 正式比赛启动脚本
- `Nginx` 统一入口配置
- 正式版上线包打包脚本

当前仓库 `2026-04-02` 已补齐以下正式比赛落点：

- `configs/competition.yaml`
- `migrations/mysql/0004_seed_competition_admin.sql`

- `scripts/reset-competition.ps1`

## 7. 推荐部署步骤

### 7.1 赛前一到两天完成

1. 准备正式比赛数据库，建议命名为 `sandbox_game_service_competition`。
2. 复制并修改正式比赛配置文件：`configs/competition.yaml`。
3. 确定比赛主机固定 IP，例如 `192.168.8.200`。
4. 确认 `Nginx` 已安装，且比赛主机允许对浏览器开放 `80` 或 `8080`。
5. 确认正式比赛库与开发 / 演练库完全隔离。

补充说明：

- 当前 `guibing` 分支的服务版正式环境，应单独创建 `sandbox_game_service_competition`。
- 如果你手里还保留制造业版正式环境，不能把服务版直接指到原来的制造业正式库，否则会把两套比赛数据混在一起。

### 7.2 赛前当天完成

1. 执行前端打包：

```powershell
cd "E:\project\sand box game\frontend"
npm run build
```

2. 构建后端或准备正式运行命令：

```powershell
cd "E:\project\sand box game"
go build -o bin/sandbox-game-server.exe ./cmd/server
```

3. 初始化正式比赛数据库：

```powershell
cd "E:\project\sand box game"
.\scripts\init-competition.ps1 -ConfigPath .\configs\competition.yaml
```

说明：

- 本脚本只初始化 `sg_game_config` 与 `admin` 账号，不会直接创建玩家组和玩家账号。
- 正式比赛环境需要由管理员首次登录后，在 `赛前配置页` 中配置 `groupCount` 并点击“初始化比赛”。

4. 启动正式后端服务：

```powershell
cd "E:\project\sand box game"
.\scripts\start-competition.ps1 -ConfigPath .\configs\competition.yaml
```

5. 按样例配置 `Nginx`：

- 配置文件样例：`scripts/nginx/sandbox-game.competition.conf`
- 核心口径：
  - `/` 指向前端 `dist`
  - `/api/` 反向代理到 `http://127.0.0.1:8080`

6. 由管理员电脑和至少一台玩家电脑分别验证：

- 登录页可访问
- 管理员可登录
- 管理员未初始化时默认进入 `赛前配置页`
- 管理员完成赛前初始化后默认进入管理端首页
- 玩家可登录
- 玩家默认进入 `0年经营页`

### 7.3 比赛开始前最后确认

统一下发访问地址，例如 `http://192.168.8.200`。
不要下发开发机个人地址、`localhost`、`127.0.0.1`、`5173` 开发入口，或后端裸 API 地址。

---

## 8. 赛前检查清单

1. 比赛主机与所有参赛电脑在同一局域网
2. 统一访问地址可从多台电脑打开
3. 登录页可访问
4. 管理员账号可登录
5. 管理员首登后可进入 `赛前配置页`
6. 管理员完成初始化后，至少两个玩家账号可登录
7. 正式比赛库不是开发库，不是演练库
8. 防火墙未拦截正式访问端口
9. 管理员已拿到账号发放清单
10. 主持人已确认最终年份配置方式
11. 数据库已完成开赛前备份

---

## 9. 现场运行建议

建议现场至少明确三类职责：

- 主持人 / 管理员：推进比赛流程，操作管理端
- 技术支持：保障比赛主机、服务、网络稳定
- 参赛玩家：使用各自账号进行经营与财报填写

比赛开始后，不建议进行以下行为：

- 临时改代码
- 临时改数据库结构
- 临时替换 Excel 字段口径
- 在正式比赛主机上继续开发调试

---

## 10. 备份与恢复建议

首版建议至少在以下时点做数据库备份：

1. 开赛前，初始化完成后
2. 初始基线提交后
3. 每个正式比赛年结束后
4. 比赛结束后

若比赛现场出现严重故障，恢复顺序建议为：

1. 优先恢复服务进程
2. 若数据库损坏，再恢复最近一次正式比赛库备份
3. 恢复后先由管理员验证数据，再通知玩家继续

---

## 11. 首版不建议的做法

- 使用开发者个人电脑直接作为正式比赛主机，同时继续开发
- 直接让玩家访问 `Vite` 开发服务地址
- 让正式比赛环境与开发库共用数据库
- 在比赛进行中临时切换到另一套未经验证的配置文件

---

## 12. 结论

首版正式比赛最推荐的不是“继续使用开发机联调模式”，而是：

- 一台专用比赛主机
- 一套专用正式比赛库
- 一个统一访问地址
- 前端打包后由 `Nginx` 提供
- Go 服务专注提供 API

对现场参赛人员来说，最理想的正式入口应收口为：

- `http://<比赛主机IP>`

这也是首版最稳、最容易现场控制、最符合当前业务场景的上线方式。
