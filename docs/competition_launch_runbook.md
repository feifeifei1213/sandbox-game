# 沙盘经营系统正式比赛上线方案（首版）

> 更新日期：2026-08-03
> 适用方式：基于《正式需求文档（首版）》《技术选型细化文档（Go 方向）》《联调与人工验收运行手册（首版）》与当前项目实现状态，定义首版正式比赛的推荐部署方式、环境边界、部署步骤与现场保障口径。  
> 文档定位：本文件回答“正式比赛时系统应该部署在哪里、用户访问什么地址、赛前要准备什么、现场如何保障稳定运行”。

## 1. 目标

首版正式比赛上线方案需要解决四件事：

1. 让 `10` 个玩家组账号和 `1` 个管理员账号访问同一套正式比赛系统，而不是访问开发人员本机开发环境。
2. 让前端页面与后端 API 以正式服务方式运行，不依赖 `Vite` 开发服务器长期支撑比赛现场。
3. 让正式比赛数据与开发库、演练库彻底隔离，避免测试行为污染比赛结果。
4. 让现场主持人、开发与管理员知道比赛前、比赛中、比赛后的最小操作口径。

---

## 2. 推荐上线形态

首版正式比赛推荐采用以下形态：

- 一台专用 `比赛主机`
- 一套专用 `正式比赛数据库`
- 一个统一访问地址
- 前端打包为静态资源
- Go 服务同时提供前端静态页面与业务 API
- 单实例正式入口：管理员只启动一套系统，生产制造版 / 贵宾服务版由网页赛前配置页选择

推荐访问形式：

- `http://<比赛主机IP>:<server.port>/sandbox-game/login`
- `http://sandbox-game.company.local` （若公司内网支持固定域名）

正式比赛时，玩家与管理员都不应再访问：

- 开发者个人电脑的临时地址
- `http://127.0.0.1:5173`
- `http://localhost:5173`
- 依赖开发终端常驻的 `Vite` 页面地址

---

## 3. 环境分层建议

| 环境 | 用途 | 是否允许写入 | 是否用于正式比赛 |
|---|---|---|---|
| 开发环境 | 开发、自测、调试 | 是 | 否 |
| 多组演练环境 | 主持人彩排、联调、流程验收 | 是 | 否 |
| 单组演练环境 | 单链路推演、公式回归、快速验证 | 是 | 否 |
| 正式比赛环境 | 正式比赛当天使用 | 是 | 是 |

正式比赛环境必须满足：

- 独立数据库
- 独立配置文件
- 独立账号与初始化数据
- 不与开发环境共用进程或数据

如果管理员电脑已经跑过旧比赛，还必须满足：

- 旧代码目录不被新代码覆盖
- 旧数据库先通过备份脚本导出 zip
- 新比赛使用新部署目录和新数据库

---

## 4. 比赛主机建议

比赛主机建议承担以下职责：

- 承载 Go 后端正式服务
- 承载前端打包后的静态资源
- 连接正式比赛数据库
- 对局域网内所有参赛电脑提供统一访问入口

比赛主机建议满足：

- 接入稳定电源
- 接入稳定局域网
- 使用固定内网 IP
- 比赛期间不再进行开发、改代码、热更新
- 关闭与比赛无关的软件和大流量下载任务

推荐网络口径：

- 玩家电脑、管理员电脑、比赛主机位于同一局域网
- 对浏览器开放的端口以 `competition.yaml` 中的 `server.port` 为准
- 数据库端口不对普通玩家电脑开放

---

## 5. 部署口径

首版推荐的部署结构如下：

1. 前端执行 `build`，产出 `dist`
2. Go 后端读取正式比赛配置启动，同时提供前端 `dist` 与 `/api/v1/sandbox-game/*` 接口
3. MySQL 使用正式比赛库

对现场参赛人员来说，应该感知为：

- 所有人只访问一个地址
- 登录后按角色自动跳转
- 不感知前后端分离细节
- 不需要通过不同脚本区分生产制造版 / 贵宾服务版
- 版本在管理员赛前配置页选择，初始化后锁定

## 7. 推荐部署步骤

### 7.1 赛前一到两天完成

1. 如果管理员电脑已有旧比赛数据，先在旧部署目录执行 `备份当前比赛数据库.bat` 并确认生成 zip。
2. 准备新的正式比赛数据库，建议命名为 `sandbox_game_competition`。
3. 新建新的部署目录，不覆盖旧代码目录。
4. 复制并修改正式比赛配置文件：`configs/competition.yaml`。
5. 确定比赛主机固定 IP，例如 `192.168.8.200`。
6. 确认比赛主机允许对浏览器开放 `competition.yaml` 中配置的服务端口，例如 `8080`。
7. 确认正式比赛库与开发 / 演练库 / 旧比赛库完全隔离。

### 7.2 赛前当天完成

1. 执行前端打包：

```powershell
cd "E:\project\sand box game\frontend"
npm run build
```

2. 构建后端或准备正式运行命令：

```powershell
cd "E:\project\sand box game"
go build -o bin/sandbox-game-server.exe ./cmd/server
```

3. 初始化正式比赛数据库：

```powershell
cd "E:\project\sand box game"
.\scripts\init-competition.ps1 -ConfigPath .\configs\competition.yaml
```

正式包交付给管理员后，也可以在部署目录直接双击：

```text
首次初始化数据库.bat
```

说明：

- 本脚本只初始化 `sg_game_config` 与 `admin` 账号，不会直接创建玩家组和玩家账号。
- 正式比赛环境需要由管理员首次登录后，在 `赛前配置页` 中配置 `groupCount` 并点击“初始化比赛”。

4. 启动正式后端服务：

```powershell
cd "E:\project\sand box game"
.\scripts\start-competition.ps1 -ConfigPath .\configs\competition.yaml
```

正式包交付给管理员后，也可以在部署目录直接双击：

```text
启动沙盘系统.bat
```

5. 由管理员电脑和至少一台玩家电脑分别验证：

- 登录页可访问
- 管理员可登录
- 管理员未初始化时默认进入 `赛前配置页`
- 管理员完成赛前初始化后默认进入管理端首页
- 玩家可登录
- 玩家默认进入 `0年经营页`

### 7.3 比赛开始前最后确认

统一下发访问地址，例如 `http://192.168.8.200:8080/sandbox-game/login`。
不要下发开发机个人地址、`localhost`、`127.0.0.1`、`5173` 开发入口，或后端裸 API 地址。

## 8. 赛前检查清单

1. 比赛主机与所有参赛电脑在同一局域网
2. 统一访问地址可从多台电脑打开
3. 登录页可访问
4. 管理员账号可登录
5. 管理员首登后可进入 `赛前配置页`
6. 管理员完成初始化后，至少两个玩家账号可登录
7. 正式比赛库不是开发库，不是演练库
8. 防火墙未拦截正式访问端口
9. 管理员已拿到账号发放清单
10. 主持人已确认最终年份配置方式
11. 数据库已完成开赛前备份

---

## 9. 现场运行建议

建议现场至少明确三类职责：

- 主持人 / 管理员：推进比赛流程，操作管理端
- 技术支持：保障比赛主机、服务、网络稳定
- 参赛玩家：使用各自账号进行经营与财报填写

比赛开始后，不建议进行以下行为：

- 临时改代码
- 临时改数据库结构
- 临时替换 Excel 字段口径
- 在正式比赛主机上继续开发调试

---

## 10. 备份与恢复建议

首版建议至少在以下时点做数据库备份：

1. 开赛前，初始化完成后
2. 初始基线提交后
3. 每个正式比赛年结束后
4. 比赛结束后

备份方式推荐使用正式包根目录中的：

```text
备份当前比赛数据库.bat
```

该脚本会在当前部署目录下创建或复用 `backup` 文件夹，并生成包含完整 SQL、结果摘要 CSV 和备份说明 TXT 的 zip 文件。结果摘要用于快速查看排名、收入、利润、权益、CEO / CFO 等关键结果；如需精确追溯，应将 SQL 恢复到临时数据库后查询。

若比赛现场出现严重故障，恢复顺序建议为：

1. 优先恢复服务进程
2. 若数据库损坏，再恢复最近一次正式比赛库备份
3. 恢复后先由管理员验证数据，再通知玩家继续

---

## 11. 首版不建议的做法

- 使用开发者个人电脑直接作为正式比赛主机，同时继续开发
- 直接让玩家访问 `Vite` 开发服务地址
- 让正式比赛环境与开发库共用数据库
- 在比赛进行中临时切换到另一套未经验证的配置文件

---

## 12. 结论

首版正式比赛最推荐的不是“继续使用开发机联调模式”，而是：

- 一台专用比赛主机
- 一套专用正式比赛库
- 一个统一访问地址
- 前端打包后随正式包一起交付
- Go 服务同时提供页面与 API

对现场参赛人员来说，最理想的正式入口应收口为：

- `http://<比赛主机IP>:<server.port>/sandbox-game/login`

这也是首版最稳、最容易现场控制、最符合当前业务场景的上线方式。
